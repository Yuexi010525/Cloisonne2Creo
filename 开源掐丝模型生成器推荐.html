你说：

给我找几个开源的掐丝珐琅3D打印模型生成器；我想做的是提取一张图片的颜色分界线，生成曲线函数，将曲线函数导入CAD/CREO中生成连续的线条，给我推荐一条实现路径，我将会让豆包来完成这件事

ChatGPT 说：

可以，而且我先给你一个非常关键的判断：

你想做的东西，本质上并不是一个普通的“图片转3D模型”工具，而是一个“图片颜色区域 → 共边界线提取 → 曲线重建 → CAD曲线 → 掐丝实体”的专用生成器。

我查了一圈目前公开的开源项目后，最值得你拿来给豆包参考的不是某一个完整项目，而是把几个成熟开源组件拼起来。其中有一个项目甚至已经直接实现了“Cloisonné（掐丝珐琅）模式”。

一、目前最值得关注的几个开源项目

1. 首推：Lumina-Layers

GitHub：

Lumina-Layers GitHub

这个项目和你的目标非常接近。

它目前已经公开支持：

  • 图片转多颜色模型

  • SVG 模式

  • 自动提取图像颜色

  • 背景去除

  • Outline

  • Cloisonné enamel mode（掐丝珐琅模式）

  • 自动提取颜色边界

  • 生成金属丝框

  • 金属丝可以作为独立对象输出

  • 线宽可调 0.2–1.2 mm

  • 线高可调 0.04–1.0 mm GitHub+1

而且这个项目目前是公开 GitHub 项目，仓库本身是 GPL-3.0。GitHub+1

更重要的是，它的最新版本已经明确写出了：

Cloisonné Mode - Auto-extract color boundaries to generate metal wire frames

也就是说：

你想做的核心算法，人家已经实现了一个版本。

但是它的方向更偏向：

图片 → 多色3D打印 → 3MF

而你真正想做的是：

图片 → 颜色边界 → CAD连续曲线 → Creo → 生成掐丝结构

所以我建议你不要直接照搬 Lumina 的最终3MF流程，而是重点研究它的：

图像分色 → 区域识别 → 边界提取 → 掐丝线生成

这几个部分。

2. VTracer

GitHub：

VTracer GitHub

这是我非常推荐豆包研究的第二个项目。

它的核心作用是：

Raster Image → Vector SVG

也就是：

PNG/JPG
↓
矢量路径
↓
SVG Path

它和传统 Potrace 最大的区别是，VTracer可以处理彩色图片，并且有自己的图像处理和颜色聚类流程，不仅限于黑白二值图。GitHub

对于你的项目来说，它可以承担：

“把颜色区域边缘变成平滑矢量曲线”

这个工作。

不过有一个问题：

VTracer得到的是“图形轮廓”，而你需要的是“颜色区域之间的共边界中心线”。

这两者并不完全一样。

所以我不会让豆包直接：

图片 → VTracer → SVG → 掐丝

而是：

图片 → 颜色分区 → 区域边界 → 去重 → 曲线拟合

3. image-to-svg

GitHub：

image-to-svg GitHub

这个项目也非常有参考价值。

它采用：

K-Means颜色聚类 + Potrace / VTracer

的组合。

也就是说：

图片
↓
颜色聚类
↓
多个颜色区域
↓
每个颜色区域进行矢量化
↓
SVG

它甚至提供了 Python/Potrace 和 TypeScript/VTracer 两套实现。GitHub

对于你来说，它非常适合拿来研究：

“一张复杂彩色图，如何自动拆成若干颜色区域。”

4. vectorizer

GitHub：

vectorizer GitHub

这个也很有意思。

内部采用 Potrace 做多颜色矢量化。GitHub

如果以后让豆包做一个 Web 小工具，这个项目的思路非常值得参考。

6. Potrace

官方开源路线：

Potrace GitHub镜像

Potrace本身是非常经典的：

Bitmap → Vector

而且它可以直接输出：

  • SVG

  • DXF

  • EPS

  • PDF

  • GeoJSON

等格式。GitHub

所以如果你的输入最终被处理成：

某一种颜色 = 黑色
其它全部 = 白色

那么 Potrace 非常适合拿来做单色区域的曲线重建。

7. svgpathtools

GitHub：

svgpathtools GitHub

这个不是“图片转模型工具”。

但是对于你的项目来说，我反而认为它是非常重要的底层库。

因为它可以直接处理：

  • Line

  • Quadratic Bezier

  • Cubic Bezier

  • Arc

  • Path

而且能够：

  • 计算曲线长度

  • 计算切线

  • 计算曲率

  • 查找交点

  • 拆分曲线

  • 平滑曲线

  • SVG Path 和 Bézier 转换

  • Bézier 与多项式之间转换 GitHub+1

这意味着它特别适合完成你说的：

“生成曲线函数”

实际上我建议不要真的把每条线变成一个复杂的数学函数 y=f(x)。

而是采用：

参数曲线

例如：

x=x(t) y=y(t) 0≤t≤1

或者更实际一点：

三次Bezier

P(t)=(1−t)3P0​+3(1−t)2tP1​+3(1−t)t2P2​+t3P3​

这比强行生成 y=f(x) 更适合掐丝，因为：

一条闭合曲线很可能存在一个 x 对应多个 y。

三、这里有一个非常重要的技术变化

你刚才说：

“提取一张图片的颜色分界线”

这个思路是对的。

但是一定不要设计成：

红色区域 → 提取轮廓
蓝色区域 → 提取轮廓
绿色区域 → 提取轮廓

然后全部叠起来。

因为这样会产生：

红色边界
    +
蓝色边界

实际上同一条边界会被提取两次。

最后你的掐丝可能变成：

========
========

两根线贴在一起。

真正正确的是：

红区域 | 蓝区域

        ↓

     一条公共边界

也就是建立：

Region Adjacency / Shared Boundary

真正的核心不是：

“识别颜色”

建立颜色区域拓扑关系

A-C

   └──── Boundary A-D

而不是简单地把每个区域描边。

五、而且我建议你不要把“曲线函数”作为第一输出格式

19. Bézier曲线数据结构

统一内部数据：

{
  "type": "cubic_bezier",
  "p0": [0,0],
  "p1": [10,5],
  "p2": [20,5],
  "p3": [30,0]
}

公式：

P(t) =
(1-t)^3 P0
+ 3(1-t)^2 t P1
+ 3(1-t)t^2 P2
+ t^3 P3

0 <= t <= 1

20. 为什么不要强制使用 y=f(x)

禁止把全部曲线强制表示为：

y = f(x)

因为复杂闭合曲线可能存在：

一个X对应多个Y

因此内部标准必须采用：

x(t)
y(t)

参数曲线。

74. 关于IBL格式的特殊要求

由于不同Creo版本对导入格式的具体解析可能存在差异：

不要假设某种IBL文本格式一定适用于所有版本。

必须：

  1. 把IBL格式封装成独立Exporter。

  2. 支持配置Creo/IBL版本模板。

  3. 预留测试样本。

  4. 允许以后根据实际Creo导入情况修改Exporter。

  5. 不影响核心Curve数据结构。

也就是说：

内部Curve
      │
      ├── SVGExporter
      ├── DXFExporter
      └── IBLExporter

不能：

核心算法直接生成IBL

这版的关键是我特意把**“颜色区域轮廓”和“颜色区域公共边界”区分开了**，这是整个项目最容易做错、但又最核心的一步。

建议第一版先让豆包做到 Phase 1～Phase 3，也就是“图片 → 分色 → 公共边界 → 平滑曲线 → SVG预览”。这一关跑通以后，再接 DXF/IBL/Creo，成功率会高很多。
