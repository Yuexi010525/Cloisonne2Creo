# ISSUE: 线稿中粗线变成两条（或多条）线

> 状态：待 ChatGPT 评审解决方案方向
> 报告人：豆包（执行端）
> 复现图：`cloisonne-generator/examples/test_user_lineart.png`（用户上传的黑白卡通线稿）

---

## 1. 问题现象

对**黑白线稿**（黑线 + 白底）输入，生成结果中**原本一条粗黑笔画，在输出曲线里变成两条近重合的平行线**（沿笔画左右边缘各一条），部分位置甚至出现多条线。

可视化确认（红线=生成曲线叠加在黑线稿上，放大头部局部可看到粗笔画处有两条平行红线）：

- 边界总数：**222 条**（正常色块图案约 20 条）
- 连续曲线组：**217 组**（几乎每条边界独立成组）
- 自交冲突：**23**
- 线距冲突：**319**
- 小半径：**72**
- 验证状态：**error**（断线 0，但拓扑全面爆表）

## 2. 复现方式

```python
CloisonnePipeline(config={
    "color_precision": 6, "filter_speckle": 4, "mode": "spline",
    "hierarchical": "cutout", "smoothness": 0.7, "gen_outline": False,
})
# 输入: test_user_lineart.png（黑白线稿）
```

## 3. 直接证据（数据）

### 3.1 VTracer 把黑线拆成 160+ 个深灰 region

对黑白线稿运行 VTracer（`hierarchical=cutout, mode=spline`），输出 **442 个 path / 175 个有效 region**，其中**深色 region（灰度<120）约 105~112 个**。VTracer 原始输出颜色分布：

```
#181818: 18   #272727: 18   #1D1D1D: 17   #212121: 17
#252525: 17   #222222: 17   #242424: 17   #1B1B1B: 17  ...（几十种近黑灰度）
```

### 3.2 与 color_precision 无关

| color_precision | region 数 | 深色 region | 边界数 | 自交 |
|---|---|---|---|---|
| 3 | 173 | 112 | 240 | 44 |
| 4 | 166 | 105 | 209 | 25 |
| 6 | 175 | 105 | 217 | 23 |
| 8 | 182 | 106 | 223 | 29 |

即使 `color_precision=3`，黑线仍被拆成 112 个深色 region → **不是颜色量化精度问题，是 VTracer cutout 对细长黑色笔画的固有切分行为**。

### 3.3 区域对之间出现重复边界

同一对 region 之间存在 **2 条边界**（如 R37-R74: 2、R48-R166: 2、R50-R127: 2…），说明同一几何边界被重复提取。

## 4. 根因链

1. **黑白线稿的黑线有抗锯齿灰度渐变**（黑→灰→白过渡），VTracer 把不同灰度分割成独立 path/region；
2. 每条粗黑笔画被拆成**多个相邻的深灰 region**（笔画的"核心/边缘"或"左半/右半"）；
3. 共享边界提取的语义是**"相邻 region 的公共边界"**：
   - 深灰 region 与白色背景的边界 → **笔画左右两条边缘线**；
   - 深灰 region 与深灰 region 的边界 → **笔画内部灰度分界线**；
4. 结果：一条粗线 → 两条（边缘）甚至多条（内部灰度分界）近重合曲线。

## 5. 架构层面的本质

当前管线是为**多色块填充图案**设计的：每个色块 = 一个 region，掐丝线 = 色块交界的**中心线**，语义正确。

但**线稿**是另一类输入：**黑线本身是"区域"**，正确的掐丝线应沿黑线的**中轴线**（skeleton / medial axis）走，而不是沿黑白交界的**边缘**走。当前"共享边界 = 区域交界"的语义在线稿场景下，天然会把粗线输出成边缘双线。

## 6. 候选解决方案（供 ChatGPT 决策）

| 方案 | 思路 | 优点 | 缺点/风险 |
|---|---|---|---|
| **A. 后处理颜色合并** | 把色差 < 阈值的相邻 region 合并（黑线所有深灰合成一个黑 region）再提取边界 | 改动小，复用现有管线 | 粗线仍输出**轮廓**（边缘），不是中心线；合并阈值需调参 |
| **B. 线稿专用模式：中轴线提取** | 检测线稿输入，对黑线区域用 skeletonize / Voronoi 提取**中轴线**作为掐丝线 | 语义正确（线稿掐丝=沿笔画中心走），正是掐丝工艺的真实做法 | 需要新算法；skeleton 在笔画交叉/粗细变化处可能有毛刺，需工程化清理 |
| **C. 输入预处理二值化** | 上传前/管线前对线稿做阈值二值化，抗锯齿灰边硬化为纯黑 | 消除灰度渐变 → VTracer 只出黑/白两色，黑线成单一 region | 只解决"碎片化"，粗线仍是边缘非中心线；可能损失抗锯齿细节 |
| **D. B+C 组合** | 二值化（消碎片）+ 中轴线提取（取中心） | 最接近线稿掐丝真实工艺 | 实现量最大 |

**建议优先级**：B（中轴线）是线稿场景的正解，但工程量大；A 是短期可落地的缓解。需 ChatGPT 确认是否值得为线稿增加独立处理分支，以及中轴线提取的工程要求（交叉点处理、中心线 G0/G1 连续性、与现有导出格式的衔接）。

## 7. 附带发现（次要）

- 大量碎片 region 使 `_prune_overlap` 的 O(n²) 重叠裁剪性能劣化（222 边界时单次分析 >15s），需要性能优化或对碎片场景跳过。
- 验证器在线稿碎片场景下自交/线距冲突爆表（319 条线距冲突），属**真实现象**（碎片间边界真实贴近），并非误报，但数量上不可用。
